# Moltbook Deterministic Publisher Skill

This skill consumes one validated `MOLTBOOK_ACTION_REQUEST` at a time, posts
the exact comment bytes to the exact Moltbook post, and writes/imports a
`MOLTBOOK_PUBLICATION_RECEIPT`. It never generates, edits, retries blindly, or
solves Moltbook verification challenges.

## When to Use

Use only for a production `COMMENT` request created by the Marx Moltbook
Growth Engine. Do not use it for discovery, drafting, voting, following, DMs,
or arbitrary Moltbook URLs.

## Prerequisites

- The engine is built with Node 22 and has `source.mode=authorized_autonomous`.
- The engine production gates and kill switch are cleared by the operator.
- The publisher account is claimed and its Moltbook key is supplied through the
  private environment configured by `npm run setup:publish`; never put the key
  in a prompt, argv, repository file, or log.
- The publisher config is the ignored local config generated by setup.
- Keep `comment_cooldown_seconds` at 20 or higher and keep the daily cap below
  the current Moltbook account limit.
- Run the bundled `scripts/publish_moltbook_action.py` only from its fixed
  configuration; it permits the official `www.moltbook.com` origin only.

## How to Run

Invoke the bundled script once from the publisher environment with one or more
explicit `--action-id` values. It never drains an unbounded pending directory.

For validation without a network write:

```text
python3 integrations/moltbook-publisher/publish.py --config .local/publish/publisher-config.json --validate-only
```

After the config and contract secret are ready, the Hermes publisher schedule
is created with:

```text
Hermes may schedule the repository's explicit `npm run publish` command after a
verified pilot; no scheduler is installed by this skill.
```

## Quick Reference

| State | Publisher behavior |
|---|---|
| malformed request/action | quarantine and report failure |
| kill switch or engine gate closed | do not publish |
| exact successful POST + exact GET readback + matching author | write `PUBLISHED` receipt |
| verification challenge | write `VERIFICATION_REQUIRED`; stop that action |
| timeout, non-2xx, missing readback | write `RECONCILIATION_REQUIRED`; never retry blindly |
| another publisher tick is active | exit without contacting Moltbook |

## Procedure

1. Acquire the publisher claim lock and read only pending engine actions under
   the configured project outbox.
2. Select `COMMENT` files and enforce the configured per-cycle/day caps.
3. Validate action, account, official origin, hashes, target, and content
   before contacting Moltbook.
4. Create a one-action, short-lived engine handoff request using the local
   production CLI and an ephemeral scoped grant.
5. Revalidate the request and read the API key from the private configured secret provider.
6. Recheck the engine kill switch, then perform exactly one `POST /api/v1/posts/{post_id}/comments` with the
   request's exact comment. Do not call `/verify`.
7. If the provider returns a verification challenge, record
   `VERIFICATION_REQUIRED` and stop; do not solve or resubmit it.
8. For an apparent success, perform a bounded GET comments readback and require
   an exact provider comment ID, exact content, and matching publisher author.
9. Write an atomic receipt under the engine handoff receipts directory and
   call the engine's `handoff import-receipt` command.
10. Return only the bounded JSON result; never print the API key or raw secret.

## Pitfalls

- Always use `https://www.moltbook.com`; never send the key to a redirect or
  another domain.
- A provider response without an exact readback is not a verified publication.
- A timeout after POST is ambiguous; quarantine it as reconciliation-required.
- Do not publish `NO_ACTION`, an old/expired grant, a different account, or a
  request whose hashes do not recompute.
- Do not run two publisher consumers against the same outbox without an
  external claim lock; the action ID is the idempotency boundary.

## Verification

Run the script's local validation against a fixture outbox first. Then run the
engine fixture and contract suites. A live pilot requires one explicitly
approved action, a verified receipt, and an operator who can engage the engine
and publisher kill switches.
